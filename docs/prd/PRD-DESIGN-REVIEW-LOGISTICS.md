## 二、~~设计审核（Design Review）~~（已废弃，2026-06-04）

> **[2026-06-04 废弃]** 本节描述的设计审核队列、美工专属 Design Lab 审核模式、确认同步、退回操作均已停用。
> 对应代码路由（`/admin/design-review`）和 API 端点可注释保留，无需删除。
> 新生产流程见「第八节：简化生产流程」。

### 2.1 背景（历史存档）

客户在 Design Lab 完成设计并下单后，系统生成一张合成效果图，但该效果图不能直接用于印刷生产，需要美工介入，进入专属的 Design Lab 审核模式，**仅调整尺寸和位置**以确保符合印刷规范（如设计不超出安全区、印刷尺寸足够清晰），不改动客户的其他设计内容。确认无误后点击「确认同步」，效果图才正式关联到订单，可对外可见。

### 2.2 用户角色

| 角色 | 权限 |
|------|------|
| 美工 | 查看审核队列、进入 Design Lab 审核模式、确认同步、退回 |
| 运营 / 管理员 | 查看队列（只读），无法操作审核动作 |
| 客户 | 下单后只能看到「设计中」状态，看不到效果图，直到同步完成 |

### 2.3 设计审核状态流转

```
PENDING_REVIEW（待审核）
       ↓ 美工开始审核
IN_REVIEW（审核中）
       ↓ 两个出口
 SYNCED（已同步）     REJECTED（已退回）
   效果图可见            客户重新提交 → 回到 PENDING_REVIEW
```

| 状态 | 客户/运营看到的订单状态 | 效果图可见性 |
|------|----------------------|------------|
| `PENDING_REVIEW` | 设计中 | 不可见 |
| `IN_REVIEW` | 设计中 | 不可见 |
| `REJECTED` | 设计中（需客户修改） | 不可见 |
| `SYNCED` | 待生产 | 可见 |

### 2.4 功能需求

#### 审核队列页（`/admin/design-review`）

**统计卡片（实时）：**
- 待审核数量
- 审核中数量
- 已退回数量
- 紧急数量（等待超过 24 小时自动标记为紧急）

**筛选：** 全部 / 待审核 / 审核中 / 已退回

**列表字段：**
- 订单号（可点击跳转订单详情）
- 客户姓名 + 邮箱
- 商品名称 + 颜色 / 尺码 + 数量
- 当前审核状态 + 紧急标记
- 等待时长（>24h 标红加粗）
- 下单时间
- 客户合成的效果图缩略图（未上传则显示「待上传」）

**操作按钮：**
- **进入 Design Lab 审核**：在新标签页打开该订单的 Design Lab 审核模式
- **退回**：弹出退回弹窗

**刷新：** 每 30 秒自动刷新。

---

#### 美工专属 Design Lab 审核模式

与客户使用的 Design Lab 区别：

| 功能 | 普通用户 | 美工审核模式 |
|------|---------|------------|
| 网格辅助线 | 不显示 | ✅ 显示，间距可配置 |
| 参考线（印刷边界 / 出血区） | 不显示 | ✅ 显示，安全区、出血区醒目标注 |
| 尺寸标注 | 不显示 | ✅ 实时展示设计区域宽高（厘米/英寸） |
| DPI / 分辨率提示 | 不显示 | ✅ 当分辨率低于 150DPI 时红色警告 |
| 设计编辑权限 | 完整编辑 | ⚠️ 仅允许调整**尺寸与位置**（缩放、移动），不可更改颜色、图案、文字内容、素材 |
| 保存方式 | 保存到草稿 | 「确认同步」保存最终效果图 URL 到订单 |
| 退出保护 | 提示保存 | 未同步时关闭页面需二次确认 |

美工调整设计时，**仅能对设计元素做尺寸和位置的微调**，目的是确保印刷区域合规，不得修改客户的图案内容、颜色、文字。原始客户提交的设计数据保留不变，美工修改的是独立的审核版本，仅在点击「确认同步」后才覆盖订单的 `mockupUrl`。

---

#### 确认同步操作

美工在 Design Lab 审核模式中调整完毕后，点击「确认同步」：
1. 前端按位置导出各视图的纯图案 PNG（见 4.5），上传获取 CDN URL，组装 `printSpecs`
2. 系统生成最终效果图（Mockup），将 URL 写入 `Order.mockupUrl`
3. 将 `printSpecs`（含各位置 `artworkImageUrl`）写入 `Order.printSpecs`
4. 订单 `designReviewStatus` 更新为 `SYNCED`，记录同步时间
5. 订单对客户/运营展示效果图，状态变为「待生产」
6. 若该订单物流信息已存在，自动标记可生成 Gang Sheet

---

#### 退回操作

美工点击「退回」后弹出弹窗：

**预设退回原因（下拉选择）：**
- 图片分辨率太低，建议替换 300DPI 以上素材
- 设计超出印刷安全区域，请调整位置
- 文字太小，印刷后难以辨认，建议放大
- 颜色与面料色系冲突，建议调整
- 设计内容含违禁内容，请修改
- 自定义原因（自由输入）

**退回后：**
- 订单 `designReviewStatus` → `REJECTED`，退回原因写入 `designReviewNote`
- **发送邮件通知客户**（附退回原因），引导客户重新进入 Design Lab 修改
- 客户修改重新提交后，状态自动重置为 `PENDING_REVIEW`，重新进入队列

---

### 2.5 数据模型（`Order` 表相关字段）

| 字段 | 类型 | 说明 |
|------|------|------|
| `designReviewStatus` | `String?` | 审核状态枚举 |
| `mockupUrl` | `String?` | 美工确认后的效果图 URL |
| `designReviewNote` | `String?` | 退回原因 |
| `designReviewRejectedAt` | `DateTime?` | 退回时间 |
| `designReviewSyncedAt` | `DateTime?` | 确认同步时间 |

### 2.6 API 端点

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/admin/orders/design-review/queue` | 获取审核队列 |
| PATCH | `/api/admin/orders/:id/design-review/sync` | 确认同步（传入 `mockupUrl`） |
| PATCH | `/api/admin/orders/:id/design-review/reject` | 退回（传入 `note`） |

## 三、物流管理（Logistics）

### 3.1 背景

设计同步完成后，运营每天 18:00 导出一批待发货快递订单，在外部平台采购物流面单并填写单号，再将 CSV 导入系统，触发订单状态更新和后续生产流程。

### 3.2 导出（Export）

**导出条件（同时满足）：**
- `designReviewStatus = SYNCED`
- `trackingNumber` 为空（尚未填写物流信息）
- 有收货地址（排除到店自提订单）

**导出格式：** CSV，浏览器直接下载，文件名含日期（如 `logistics-2026-05-28.csv`）

**CSV 列：**
订单号、客户姓名、收货地址、商品名称、颜色、尺码、数量

**操作时机：** 运营每天 18:00 手动点击「导出 CSV」（现阶段为人工触发，非自动定时任务）

---

### 3.3 导入（Import）

**操作方式：** 拖拽上传或点击选择 `.csv` 文件

**CSV 格式要求：**
```
订单号, 快递公司, 物流单号
PNG-20260528-001, SF Express, SF1234567890
PNG-20260528-002, Canada Post, CP9876543210
```
- `订单号` 和 `物流单号` 为必填列
- `快递公司` 为可选列（建议填写）
- 列名不区分大小写，兼容中英文列名

**上传流程：**
1. 上传后页面内预览解析结果（最多展示 50 行），显示订单号 / 快递公司 / 物流单号
2. 预览确认无误后点击「确认导入」
3. 系统按订单号匹配，逐条更新：
   - 写入 `trackingNumber` 和 `carrier`
   - 生成物流二维码（编码内容：订单号 + 物流单号）
   - 若 `mockupUrl` 已存在，自动标记该订单「可生成 Gang Sheet」
4. 导入完成后展示结果摘要：成功数 / 未找到的订单号 / 错误明细

**异常处理：**
- 订单号不存在 → 记入「未找到」列表，跳过，不中断导入
- 订单已有物流单号 → 跳过（不覆盖），记入警告
- 字段格式错误 → 记入错误列表

---

### 3.4 数据模型

| 字段 | 位置 | 说明 |
|------|------|------|
| `trackingNumber` | `Order` | 物流单号 |
| `carrier` | `Order` | 快递公司名称 |
| `Shipment` 表 | 关联表 | 快递公司 + 单号 + 状态，供物流追踪使用 |

### 3.5 API 端点

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/admin/orders/logistics/export` | 导出待发货 CSV |
| POST | `/api/admin/orders/logistics/import-csv` | 导入物流单号，返回 `{ updated, notFound, errors }` |

## 四、Gang Sheet 生产单

### 4.1 前提条件

生成 Gang Sheet 需同时满足：
- `mockupUrl` 已填写（设计已同步）
- `trackingNumber` 已填写（物流信息已录入）
- `printSpecs.positions` 有数据（Design Lab 确认同步时已导出各位置图稿）

### 4.2 Gang Sheet 布局规范

> **[2026-06-04 更新]** 区块一新增「单面/多面打印」标识；区块二每个位置行新增位置效果图（含产品底图的合成预览），与图稿图片（透明底）并列展示。

每张 Gang Sheet 对应一个订单，分两个区块：

---

**区块一（订单头部，只有一行）：**

```
┌────────────────────────────────────────────────────────────────────────────┐
│  [主效果图]  [物流二维码]  产品名称           颜色   尺码  数量  件数  印面  │
│  mockupUrl   (扫码打印面单) 如：Gildan 64000  黑色   M     1件  单件  多面  │
│  120×120px   64×64px       bold              副文字                         │
└────────────────────────────────────────────────────────────────────────────┘
```

| 字段 | 来源 | 说明 |
|------|------|------|
| 主效果图 | `Order.mockupUrl` | 正面（front）位置的合成 Mockup，120×120px 缩略图 |
| 物流二维码 | 编码内容：`{orderNumber}\|{trackingNumber}` | 运营扫此码打印物流面单；若无 trackingNumber 则显示占位符 |
| 产品名称 | `OrderItem.variant.product.name` | |
| 颜色 | `OrderItem.variant.color` | |
| 尺码 | `OrderItem.variant.size` | |
| 数量 | `OrderItem.quantity` 合计 | |
| 单件 / 多件标识 | 订单总件数 = 1 → 「单件」；> 1 → 「多件」 | 高亮色标记 |
| **单面 / 多面标识** | `printSpecs.positions.length === 1` → 「单面」；`>= 2` → 「多面」 | **[2026-06-04 新增]** 高亮色标记，方便快速识别印刷复杂度 |

---

**区块二（印刷位图稿，每个有图稿的位置占一行）：**

按「左袖 → 右袖 → 正面 → 背面」顺序排列，无图稿的位置跳过不展示。

> **[2026-06-04 更新]** 每行新增「位置效果图」列（含产品底图的合成预览），与「图稿图片」（透明底）并列，让操作人员可以直观看到该位置的印刷效果。

```
┌──────────────────────────────────────────────────────────────────────────┐
│  [位置效果图]  [图稿图片]   位置名称   印刷尺寸（cm）   印刷工艺            │
│  mockupImageUrl artworkUrl  正面        25 × 30 cm     DTF                │
│  (含产品底图)   (透明底PNG)                                                │
│  100×100px      100×100px                                                 │
├──────────────────────────────────────────────────────────────────────────┤
│  [位置效果图]  [图稿图片]   背面        15 × 20 cm     DTF                │
└──────────────────────────────────────────────────────────────────────────┘
```

| 字段 | 来源 | 说明 |
|------|------|------|
| **位置效果图** | `printSpecs.positions[i].mockupImageUrl` | **[2026-06-04 新增]** 该位置含产品底图的合成预览（见 4.5），100×100px |
| 图稿图片 | `printSpecs.positions[i].artworkImageUrl` | 纯图案层 PNG，**不含产品底图**，透明背景（见 4.5），100×100px |
| 位置名称 | `printSpecs.positions[i].position` | front / back / left / right / left_chest / right_chest |
| 印刷尺寸 | `widthCm × heightCm` | |
| 印刷工艺 | `printType` | 如 DTF、丝印 等 |

---

### 4.3 `printSpecs` 数据结构

> **[2026-06-04 更新]** 每个位置对象新增 `mockupImageUrl` 字段（含产品底图的合成效果图）。

存储于 `Order.printSpecs`（JSON 字段），由 Design Lab 客户完成设计提交时写入：

```json
{
  "positions": [
    {
      "position": "front",
      "mockupImageUrl": "https://cdn.example.com/mockup/order-id/front.jpg",
      "artworkImageUrl": "https://cdn.example.com/artwork/order-id/front.png",
      "widthCm": 25,
      "heightCm": 30,
      "printType": "DTF"
    },
    {
      "position": "back",
      "mockupImageUrl": "https://cdn.example.com/mockup/order-id/back.jpg",
      "artworkImageUrl": "https://cdn.example.com/artwork/order-id/back.png",
      "widthCm": 15,
      "heightCm": 20,
      "printType": "DTF"
    }
  ]
}
```

**字段说明：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `position` | `String` | 印刷位置枚举，见下表 |
| `mockupImageUrl` | `String` | **[2026-06-04 新增]** 该位置含产品底图的合成效果图 URL，用于生产单预览展示 |
| `artworkImageUrl` | `String` | 该位置纯图案层 PNG（透明背景），用于印刷输出 |
| `widthCm` | `Number` | 印刷宽度（厘米） |
| `heightCm` | `Number` | 印刷高度（厘米） |
| `printType` | `String` | 印刷工艺，如 `DTF`、`丝印` |

**`Order.mockupUrl` 与 `positions[i].mockupImageUrl` 的区别：**

| 字段 | 用途 | 内容 |
|------|------|------|
| `Order.mockupUrl` | 订单主效果图，展示在生产单区块一、订单列表缩略图 | 正面（front）视图的合成效果图，若无正面则取第一个有图稿的位置 |
| `positions[i].mockupImageUrl` | 生产单区块二每行的位置预览 | 该具体位置的合成效果图（含产品底图） |
```

**`position` 枚举值：**

| 值 | 中文名 | 说明 |
|----|--------|------|
| `front` | 正面 | T 恤前面 |
| `back` | 背面 | T 恤后面 |
| `left` | 左袖 | 左侧袖子 |
| `right` | 右袖 | 右侧袖子 |
| `left_chest` | 左胸 | 左胸小图 |
| `right_chest` | 右胸 | 右胸小图 |

### 4.4 打印面单流程

1. 运营打开该订单的 Gang Sheet
2. 扫描区块一中的物流二维码（编码：`{orderNumber}|{trackingNumber}`）
3. 系统触发打印物流面单（调用物流 API 或外部打印机）
4. 系统记录首次下载 / 打印时间（`gangSheetDownloadedAt`）

### 4.5 Design Lab 设计提交 — 图层导出规范（关键技术需求）

> **[2026-06-04 更新]** 原标题「确认同步」改为「设计提交」，触发时机从美工操作改为客户完成设计时自动触发。
> 新增：每个位置额外导出含产品底图的合成效果图（`mockupImageUrl`），供生产单各位置行展示。

#### 背景

Design Lab 的 canvas 包含两层：
1. **产品底图层**（product base）：T 恤/帽子等底板图片，用于 Mockup 预览
2. **图案层**（artwork）：客户上传的图片、添加的文字等设计元素

两层各有用途：

| 导出产物 | 包含的层 | 用途 |
|---------|---------|------|
| `artworkImageUrl`（透明底 PNG） | 仅图案层 | 发给印刷厂输出用 |
| `mockupImageUrl`（合成效果图） | 底图层 + 图案层 | 生产单各位置行预览展示 |
| `Order.mockupUrl`（主效果图） | 底图层 + 图案层 | 取正面视图，作为订单主缩略图 |

#### 导出流程（客户完成设计、提交前触发）

前端为每个有图案内容的视图（front / back / left / right 等）依次执行：

```
步骤 A：导出位置效果图（mockupImageUrl）
1. 保持产品底图层可见（不做任何隐藏操作）
2. 以 canvas.toDataURL('image/jpeg', 0.92) 导出含底图的合成效果图
3. 将 JPEG base64 或 Blob 上传至后端存储（返回 CDN URL）
4. 将 URL 写入 printSpecs.positions[i].mockupImageUrl

步骤 B：导出印刷图稿（artworkImageUrl）
5. 临时隐藏产品底图层（设 visibility: hidden 或 opacity: 0）
6. 以 canvas.toDataURL('image/png') 导出透明背景纯图案 PNG
7. 恢复产品底图层显示
8. 将 PNG base64 或 Blob 上传至后端存储（返回 CDN URL）
9. 将 URL 写入 printSpecs.positions[i].artworkImageUrl

步骤 C：主效果图
10. 取 position = 'front' 的 mockupImageUrl 作为 Order.mockupUrl
    若无 front 视图，取 positions[0].mockupImageUrl

步骤 D：遍历并提交
11. 重复步骤 A-B，遍历所有有图案内容的视图
12. 所有视图导出完成后，将完整 printSpecs（含 mockupImageUrl + artworkImageUrl）
    随下单请求一起提交到后端
```

#### 导出质量要求

| 产物 | 格式 | 分辨率 | 背景 |
|------|------|--------|------|
| `artworkImageUrl` | PNG（透明背景） | `pixelRatio: 2`（2x 高清，150 DPI 以上） | 完全透明 |
| `mockupImageUrl` | JPEG（quality 0.92） | `pixelRatio: 2` | 产品底色（与产品颜色一致） |
| `Order.mockupUrl` | JPEG（quality 0.92） | `pixelRatio: 2` | 产品底色 |

#### 空位置处理

若某个视图（如 `back`）用户没有放置任何图案，则该位置**不加入 `positions` 数组**，跳过导出。Gang Sheet 只展示有内容的位置。

#### 下单 API 请求格式（Design Lab → 后端）

```json
POST /api/orders/checkout（或现有下单接口，增加以下字段）
{
  "mockupUrl": "https://cdn.example.com/mockup/order-id/front.jpg",
  "printSpecs": {
    "positions": [
      {
        "position": "front",
        "mockupImageUrl": "https://cdn.example.com/mockup/order-id/front.jpg",
        "artworkImageUrl": "https://cdn.example.com/artwork/order-id/front.png",
        "widthCm": 25,
        "heightCm": 30,
        "printType": "DTF"
      },
      {
        "position": "back",
        "mockupImageUrl": "https://cdn.example.com/mockup/order-id/back.jpg",
        "artworkImageUrl": "https://cdn.example.com/artwork/order-id/back.png",
        "widthCm": 15,
        "heightCm": 20,
        "printType": "DTF"
      }
    ]
  }

## 七、~~混合购物车处理（设计商品 + 普通商品）~~（已废弃，2026-06-04）

> **[2026-06-04 废弃]** 本节内容基于设计审核流程，已随审核队列一并废弃。
> 混合购物车（设计商品 + 普通商品）下单后不再区分处理，统一进入普通订单流程。

> ~~本节于 2026-05-29 补充，来源：实际下单发现设计商品被当作普通订单处理，缺少 design review 标识。~~

### 7.1 问题背景

客户购物车可能同时包含：
- **设计商品**：来自 Design Lab，有关联的 `CartItem.designId`，印刷前需美工审核
- **普通商品**：无 designId，可直接进入生产

原有设计将 design review 作为订单级状态，且假设一张订单全为设计商品。实际场景中混合购物车会将设计商品错误地当成普通商品下单，跳过审核流程。

### 7.2 核心决策：不拆单

混合购物车**不拆分为两张订单**，保持为一张订单，原因：
- 客户只有一个订单号、一封确认邮件、一张运单
- 普通商品和设计商品须一起备货、一起发出，保证包裹完整性
- 拆单会导致物流成本翻倍、客户体验混乱

**代价**：普通商品须等待设计审核完成后才一起进入生产。对印花/DTG 类目完全可接受，因本就需要统一备货发货。

### 7.3 订单条目级别的设计标识

#### Schema 改动（`OrderItem` 表新增两字段）

| 字段 | 类型 | 说明 |
|------|------|------|
| `designId` | `String?` | 来自 `CartItem.designId`，NULL = 普通商品 |
| `designReviewStatus` | `String?` | NULL（普通商品）\| `PENDING` \| `APPROVED` \| `REJECTED` |

`CartItem.designId` 在下单时复制到 `OrderItem.designId`，此后即使购物车清空，设计关联不丢失。

#### 订单级 `designReviewStatus` 含义扩展

原有字段含义保持，新增规则：

- 下单时，若订单内 **任意一个 OrderItem 有 designId** → `Order.designReviewStatus = 'PENDING_REVIEW'`
- 所有有 designId 的 OrderItem 均 `APPROVED` → `Order.designReviewStatus` 自动升级为 `SYNCED`，订单进入生产队列
- 订单内**全为普通商品**（无任何 designId）→ `Order.designReviewStatus` 保持 `NULL`，直接进入正常流程

### 7.4 状态流转（按订单类型）

```
纯普通商品订单：
  PENDING → PROCESSING → SHIPPED → DELIVERED
  (designReviewStatus = NULL，全程跳过设计审核)

纯设计商品订单：
  PENDING → [designReviewStatus: PENDING_REVIEW → SYNCED] → PROCESSING → SHIPPED → DELIVERED

混合订单（普通 + 设计）：
  PENDING → [designReviewStatus: PENDING_REVIEW → SYNCED] → PROCESSING → SHIPPED → DELIVERED
             ↑ 普通商品在此阶段等待，不单独先行
```

### 7.5 设计审核队列适配

审核队列展示粒度从「整张订单」细化到「订单内的设计条目」：

- 审核列表每行展示：订单号 + 具体设计条目（商品名 / 颜色 / 设计缩略图）
- 一张混合订单在队列中只占 **一行**，但详情展开后可看到哪些条目是设计商品、哪些是普通商品
- 美工审核时，对每个设计条目独立操作：**批准** 或 **退回**
- 当订单内所有设计条目都批准后，系统自动将整张订单推进到 `SYNCED`

### 7.6 运单购买的保障

**规则：** 只有 `designReviewStatus = NULL`（纯普通商品）或 `SYNCED`（设计全部审核通过）的订单，才允许进入物流导出和运单购买流程。`PENDING_REVIEW` / `IN_REVIEW` / `REJECTED` 状态的订单**锁定在物流步骤之外**。

**管理后台标识：** 混合订单（既有普通商品又有设计商品）在物流列表和 Gang Sheet 中标注 ⚠️「含设计审核商品」，提示运营该运单覆盖全部条目（含设计件）。

### 7.7 Gang Sheet 多件商品适配

Gang Sheet 原设计基于单品订单，混合订单须扩展：

- **区块一**（订单头部）的「单件 / 多件」标识须统计订单全部条目的总件数（普通商品 + 设计商品）
- **区块二**（印刷位图稿）仅展示设计商品的图稿，普通商品无图稿行
- 普通商品条目在 Gang Sheet 中以独立行列出（商品名 / 颜色 / 尺码 / 数量），无图稿列，供工厂备货核对

### 7.8 下单流程改动摘要

`checkoutController.confirmOrder`（及 dev bypass）在创建订单时：

1. 遍历 `cart.items`，将 `CartItem.designId` 复制到对应 `OrderItem.designId`
2. 若 `CartItem.designId` 存在 → `OrderItem.designReviewStatus = 'PENDING'`
3. 若订单内任意 OrderItem 有 `designId` → `Order.designReviewStatus = 'PENDING_REVIEW'`
4. 否则 `Order.designReviewStatus` 保持 `NULL`

## 八、简化生产流程（2026-06-04 新增）

> 本节为当前生效的生产操作规范，替代废弃的设计审核流程（第二节）。

### 8.1 背景与动机

原「设计审核」流程引入了美工专属审核队列、确认同步、退回等环节，实际使用中流程过重。
**新流程决策（2026-06-04）：**
- 客户付款完成后，订单**直接**进入 Orders 列表，无需美工审核即可可见
- 美工**无需**进入专属 Design Lab 审核模式，也**无需**操作确认同步或退回
- 美工在订单详情页内即可完成所有生产准备操作

### 8.2 新流程描述

```
客户在 Design Lab 完成设计 → 下单付款成功
         ↓
订单立即出现在管理后台 Orders 列表 + 客户账户「我的订单」
（状态：PENDING 或 PROCESSING，与普通订单一致）
         ↓
美工打开订单详情页
         ↓
订单详情页底部展示「生产单」区块（含效果图、各印刷位图稿、规格）
         ↓
美工操作（三个入口）：
  1. 「查看生产单」→ 打开 Gang Sheet 完整页面
  2. 「下载设计稿」→ 下载各印刷位 PNG 文件（透明背景，用于印刷）
  3. 「打印生产单」→ 触发浏览器打印对话框，打印 Gang Sheet
         ↓
进入印刷生产
```

### 8.3 订单详情页「生产单」区块（UI 需求）

**显示条件：** 该订单含有 `OrderItem.designId` 不为 NULL 的条目（即设计商品）。

**区块位置：** 订单详情页底部，在「物流信息」之后，独立卡片展示。

**区块内容：**

| 元素 | 说明 |
|------|------|
| 主效果图 | `Order.mockupUrl` 展示为缩略图，120×120px |
| **单面 / 多面标识** | `printSpecs.positions.length === 1` → 显示「单面打印」徽章；`>= 2` → 显示「多面打印」徽章（**[2026-06-04 新增]**） |
| 印刷位列表 | 来自 `Order.printSpecs.positions`，每个位置一行，展示：位置效果图（`mockupImageUrl`，含产品底图）、图稿缩略图（`artworkImageUrl`，透明底）、位置名称、印刷尺寸（cm）（**[2026-06-04 新增]** 位置效果图列） |
| 「查看生产单」按钮 | 新标签页打开 Gang Sheet 完整页（`/admin/orders/:id/gang-sheet`） |
| 「下载设计稿」按钮 | 触发打包下载所有 `artworkImageUrl`（ZIP 格式，文件名含位置名称） |
| 「打印生产单」按钮 | 打开 Gang Sheet 页后自动触发 `window.print()`，或直接在当前页触发打印 |

**印刷位列表行布局示意：**

```
┌─────────────────────────────────────────────────────────────────┐
│  [位置效果图]  [图稿图片]   正面   25 × 30 cm   DTF   [下载]     │
│  (含底图)      (透明底)                                          │
│  80×80px       80×80px                                           │
├─────────────────────────────────────────────────────────────────┤
│  [位置效果图]  [图稿图片]   背面   15 × 20 cm   DTF   [下载]     │
└─────────────────────────────────────────────────────────────────┘
```

**区块不存在时（普通商品订单）：** 隐藏整个「生产单」区块，不展示任何占位符。

### 8.4 下载设计稿规范

- 下载内容：`Order.printSpecs.positions` 中所有 `artworkImageUrl` 对应的 PNG 文件
- 打包格式：ZIP，文件名格式 `{orderNumber}-artwork.zip`
- ZIP 内文件命名：`{position}.png`（如 `front.png`、`back.png`）
- 图稿要求：透明背景 PNG，不含产品底图（由 Design Lab 确认同步时导出，见第四节 4.5）

### 8.5 打印生产单规范

- 打印内容即 Gang Sheet（见第四节，规格不变）
- 美工从订单详情点击「打印生产单」，系统打开 `/admin/orders/:id/gang-sheet` 并自动调用 `window.print()`
- 物流二维码：若 `trackingNumber` 已填写则显示二维码；未填写则显示占位符「待录入物流」
- 打印完成后，系统记录 `gangSheetDownloadedAt`（首次打印时间）
