# 成熟团队 Code Review 标准与指南

本文档包含“成熟团队”级别的代码审查标准，旨在提升正确性、可维护性、一致性和安全性。

## 1. Code Review 的目标与原则

### 目标覆盖
- **正确性**：逻辑是否符合需求？边界条件是否完整？
- **可维护性**：代码是否易读、易改？是否遵循团队约定？
- **一致性**：风格、架构边界、抽象层次是否统一？
- **安全与合规**：权限控制、数据脱敏、SQL/Command注入风险、审计要求。
- **性能与稳定性**：复杂度、资源使用、并发处理、超时与降级策略。
- **可测试性**：是否方便测试？测试用例是否覆盖了关键路径？
- **知识共享**：促进团队成员对系统与设计决策的理解。

### 核心原则
- **小 PR**：一次只做一件事，便于发现 Bug 且快速合并。
- **自动化优先**：Lint、静态分析、测试、CI 能发现的问题，不消耗人力。
- **以风险驱动投入**：核心、复杂、不熟悉的改动，Review 力度必须严格。
- **Review 是协作**：批评代码而不针对人；给出具体、可操作的建议。

## 2. 典型流程：从提交到合并

### A. 提交前（作者自检）
- **本地检查**：跑通单测/集成测试，执行 Format/Lint。
- **自我 Review**：逐行检查 Diff，重点关注新增分支与异常路径。
- **PR 描述规范**：
  - **背景/目标**：为什么改？
  - **方案与取舍**：怎么改的？替代方案是什么？
  - **风险点**：可能有什么副作用？回滚计划？
  - **测试覆盖**：怎么测的？哪些没测到？

### B. CI / 质量门禁
- **必须项**：单测/集成测试通过、Lint/Formatter 通过。
- **静态分析**：检查空指针、资源泄漏、线程安全等。
- **覆盖率**：关注“改动区域”的测试覆盖率。
- **安全扫描**：依赖漏洞、SAST、Secret 扫描。

### C. 人工 Review
- **Reviewer 配置**：至少 1-2 人，核心模块需 Owner 审批，高风险改动需 Cross-team Review。
- **结论标准**：
  - **Blocking**：必须修改的问题（Bug、安全风险、严重规范问题）。
  - **Non-blocking**：建议性修改（优化、风格偏好）。
  - **Question**：澄清疑问。

### D. 合并与上线
- **可回滚**：确保变更可以通过 Feature Flag、配置开关或版本回退进行回滚。

## 3. Review 检查清单（Checklist）

### 1) 需求与边界条件
- [ ] 输入为空、缺失或非法时，处理是否正确？
- [ ] 极值处理：0、1、最大长度、超大数值、时间边界（闰年/时区/夏令时）。
- [ ] 幂等性：重复请求是否安全？重试机制是否会导致副作用？
- [ ] 错误处理：异常是否被吞掉？失败是否误报为成功？错误码是否规范？

### 2) 数据一致性与并发
- [ ] 多线程/协程/进程是否安全？
- [ ] 竞态条件：是否存在 Check-then-Act（TOCTOU）、重复扣减、重复写入？
- [ ] 事务管理：事务边界是否正确？隔离级别是否匹配？
- [ ] 缓存一致性：写库后缓存是否失效？双写顺序是否会导致脏数据？

### 3) 资源与生命周期
- [ ] 资源泄漏：连接、文件句柄、锁、Goroutine/Thread 是否正确释放？
- [ ] 超时与取消：Context/Cancellation 是否贯穿调用链？数据库/API 调用是否有超时设置？
- [ ] 重试风暴：重试是否有上限和退避策略（Backoff）？

### 4) 安全
- [ ] 注入攻击：SQL、命令、模板注入防护是否到位？
- [ ] 权限校验：是否在后端做了严格校验（不仅仅依赖前端）？
- [ ] 敏感数据：日志中是否包含 Token、密码、PII 信息？
- [ ] 输入/输出：输入校验是否严格？输出编码是否防止了 XSS？

### 5) 可观测性与故障处理
- [ ] 关键路径是否有足够的日志、指标（Metrics）和追踪（Trace）？
- [ ] 错误上下文：报错信息是否包含请求 ID、用户 ID、关键参数？
- [ ] 稳定性模式：是否需要降级、熔断、限流？失败后是否可自动恢复？

### 6) 结构与可维护性
- [ ] 命名规范：命名是否准确表达意图？是否有误导性？
- [ ] 代码复杂度：复杂函数是否应该拆分？抽象是否过度或不足？
- [ ] 架构分层：业务规则是否混入 Controller/Handler？DB 操作是否泄露到 Service 层之外？

## 4. 高效找 Bug 战术

### 战术 A：Diff 导向法
1.  **看范围**：哪些模块被触及？是否有越界修改？
2.  **抓控制流**：检查新增的 if/else、early return、循环和异常分支。
3.  **抓状态**：检查数据库写入、缓存更新、全局变量修改。
4.  **查重构**：确保重构代码中没有混入隐蔽的功能变更。

### 战术 B：失败路径思维
- 关注网络超时、依赖服务不可用、空返回、部分成功等场景。
- 思考重试后是否会产生重复副作用。

### 战术 C：要求“证明”
- 对于复杂改动，要求作者证明不会破坏现有逻辑。
- 询问：哪些场景没测？为什么？需要 Feature Flag 吗？

### 战术 D：防微杜渐
- 发现 Bug 后，不仅仅是修复，还要考虑：
  - 加单测回归。
  - 加静态分析规则。
  - 加运行时断言。
  - 加监控告警。
